## 一、读聊天记录（合并转发）：全部报 `Connection closed`

**她的原话**
> 调 get_forward_msg，三个不同的转发 id 全都是同一个错「Connection closed」，一次都没成功过，所以转发里的内容我完全看不到

**现象**
- 三个不同 id，报错完全一样，且**没有任何前缀**
- 正常失败应该带「查看合并转发失败：…」前缀，纯 `Connection closed` 说明请求没走到业务层就断了

**排查过程（走过一条弯路）**
1. 先怀疑 bridge 到 SnowLuma 的连接断 → 给 `bot.raw` 加了重试。**改错地方了**，但无害，保留。
2. 翻 `state/bridge.log`（1572 行）发现：**一条「合并转发」记录都没有** → 请求压根没到 bridge 那层
3. 确认 MCP server 进程**没有崩**（`state/mcp-snowluma.log` 只有重启时的 `exit code=0`）
4. 直连 SnowLuma 测 `get_forward_msg`：**385ms 正常返回** → SnowLuma 本身没问题

**推断的根因**
bridge 收到请求后 `await bot.raw('get_forward_msg')` 在等 SnowLuma 把整段聊天记录拉下来（几十条消息 + 图片），这期间 handler 既不回包也不写日志（`log()` 写在拿到数据之后）。上游 DSH 的工具调用等不及，先把 MCP 连接关了 → AI 只看到 `Connection closed`。

**已改**
| 文件 | 改动 |
|---|---|
| `src/qq-model-view.js` | `compactModelData` 加深度上限（12 层）+ WeakSet 环检测，防栈溢出把进程带走 |
| `src/mcp-snowluma-safe.js` | 加崩溃日志 `state/mcp-snowluma.log`（未捕获异常 / 未处理拒绝 / 退出码） |
| `src/bridge.js` | 转发拉取加 **25 秒超时**；入口先记「合并转发查询开始」；嵌套预览 10 秒；瞬时断连重试 3 次 |

**状态**：~~⚠️ 未验证成功~~ → ✅ **真正根因已找到并修复（2026-10-21 第二轮）**，上面的「推断的根因」是错的。

**真正根因：回包太大，被 MCP stdio 客户端掐断**
- 她 16:20–16:40 读的三个 id 其实是**同一条 38 张图的转发**（被发了三次）。bridge 4 秒内就正常返回了（`合并转发查询开始` 有记录，成功分支本来就不写日志）
- MCP server 把第一批 15 张原图（其中一张 PNG 3.4 MB）塞进一条回包 → **11 MB**
- MCP stdio 客户端单条消息上限 **10 MB**（本地 SDK 1.30 的 `STDIO_DEFAULT_MAX_BUFFER_SIZE`；DSH 自带的 `@modelcontextprotocol/client` 2.2.0 同样是 10 MB）→ 超限直接关连接 → server 的 stdin 关闭、`exit code=0` 正常退出（所以崩溃日志里只有 `code=0`）
- `media.maxBytes=8MB` 是按**原始字节**算的，base64 后 ×1.33 ≈ 10.7 MB，正好越线。10-19/10-20 读成功的转发图都小，所以以前没炸
- 复现方式：用 SDK 的 `StdioClientTransport` 起 `mcp-snowluma-safe.js` 调 `qq_get_forward_msg` → 4.5 秒后 `Connection closed`，与她看到的完全一致

**第二轮修改**
| 文件 | 改动 |
|---|---|
| `src/mcp-snowluma-safe.js` | ① 所有工具统一套 `fitStdioBudget`：图片 base64 合计 >6 MB 的从后往前丢并明说丢了几张 ② `qq_get_forward_msg` 按同一预算装图，装不下的留给下一页，`imageOffset` 从第一张没发的算起（不会跳图）；单张就超预算的跳过并计入已处理（防翻页卡死）；图片编号改为全局序号 |
| `src/bridge.js` | `fetchMediaData` 里 >1 MB 的静态图先用 ffmpeg 缩到长边 ≤1600 的 JPEG（不放大小图，实测 3.4 MB PNG → 388 KB）；总量按压缩后大小计 |
| 备份 | `src/*.bak-forward-budget` |

**验证**：用真实 token 走 stdio 调三个 id 全部成功（未重启 bridge 时：7 张 / 4.4 MB，`imageOffset=7` 翻页正确拿到第 8 张）。**DSH 里实测待重启后确认**（MCP server 随 DSH 重启生效；压缩随 bridge 重启生效，生效后一批应能装下 15 张）。

## 二、抖音自主观看：三类报错

### 2.1 「自主观看必须有同一真实作品的有效采样画面」—— 0 次就挂

**她的原话**
> 这一轮 0 次就挂了，刚开跑第一拍就没过

**根因（两处叠加）**
1. `core.mjs` 的 `capture()` 用 `state.video?.id !== before.id` **严格比较**。抖音 id 会读成 `null` / `undefined` 抖动，`null !== undefined` 成立 → 判定「采样期间切换作品」→ 直接 `break`，**一帧都不剩**。于是 `imageStatus` 写着「本次操作没有采集画面」
2. `autonomous-watch.mjs` 第 168 行是**裸调用** `watchDecisionMessages(observation)`，不在任何 try/catch 里。我前一天打的「重采样」补丁只包住了后面的 `decideWatch`，前面这道预检漏了 —— 等于补丁没打

**已改**
| 文件 | 改动 |
|---|---|
| `core.mjs` | `sameWork()`：只有两边都读出有效 id 且不相等才算真换条；帧上记 id 改成「哪边读得出用哪边」 |
| `autonomous-watch.mjs` | 预检也降级为重采样（连续 5 次才对不上才认输，防死循环）；`decideWatch` 的 resample 也加了同样的计数 |

**状态**：✅ **已验证通过**。实测采样 3 帧、时间点前进（3.06s → 4.65s → 6.19s）、id 一致、`viewing.accepted: true`、`imageStatus`「已向模型提供 3 张画面」。

### 2.2 「未确认切换到另一条作品，已停止自主观看」

**她的原话**
> 翻下一条时没读到新作品就停

**根因**
`autonomous-watch.mjs` 的 `skip` 分支：`douyin_next` 之后只要 `changed !== true` 或 id 没变，就 `throw failure(...)` 结束整轮。抖音加载慢一拍、视频还没挂上去，一次没读到就判死。

**已改**
`autonomous-watch.mjs`：翻下一条最多试 **3 次**（间隔 900ms），三次都没动静才真停；每次重试记一条 `watch.next_retry` 事件。

**状态**：🔧 已改，**未实测**（需要重启后跑一轮才知道）。

### 2.3 「当前页面没有唯一可核对的评论输入框」—— needs_user

**她的原话**
> 当时看的是条用代码一帧帧拼星空蛋糕的生日动画，弹幕满屏谢谢和生日祝福

**根因（调查到的真实页面结构）**
现场翻了她卡住的那条视频（#生日代码、星空蛋糕、9185 条评论），三个问题：

1. **评论区默认收起**：输入框只有面板展开后才在 DOM 里
2. **评论图标页面里有 3 个**：y=-478（上一条）、y=699（当前这条）、y=1877（下一条）。Playwright 的 `visible` 只看尺寸和 display，**不看元素在不在屏幕内**，所以三个都算"可见"，盲点第一个会点到上一条
3. **评论框是两段式**：`.comment-input-container` 在，但里面**没有 contenteditable / textarea**，只是一个显示「留下你的精彩评论吧」的**假框**；点它一下真编辑器才出现（`div[contenteditable=true].public-DraftEditor-content`）。原选择器直接找 `.comment-input-container [contenteditable="true"]`，因此**永远是 0 个**
4. **判定又太硬**：`confirmed !== true` 就 `throw failure(..., 'needs_user')` 结束整轮

**已改**
| 文件 | 改动 |
|---|---|
| `comment-browser.mjs` | ① 先展开评论区（`feed-comment-icon`，只认视口内那个）② 再点假框激活真编辑器 ③ 发布按钮改成「输入后再找」而不是输入前就判定（空输入时页面上根本没有发送按钮） |
| `autonomous-watch.mjs` | 「确定没发出去」（`deliveryUncertain=false`）不再终止整轮，只记 `watch.comment_skipped` 跳过这条继续看。只有 `deliveryUncertain=true`（可能已发出）才停下让人核对 |

**状态**：🔧 部分修好，**评论大概率还是发不出去**
- ✅ 输入框激活已验证：点击前 editors=0，点击后 editors=1（`public-DraftEditor-content`）
- ✅ 文字确认能输进去（`innerText` 变成 `测试abc`，测完立刻清空，没留草稿）
- ❌ **发布按钮始终找不到**：输入框右侧 `commentInput-right-ct` 只有一个添加图片的按钮，全页面遍历也没有「发送/发布」

**还差**：发布按钮到底在哪。可能是回车提交（不敢试，怕真的把评论发出去），或者需要别的输入方式触发 React 状态。

## 三、共同模式（这才是根子上的问题）

三个抖音报错 + 转发报错，其实是**同一个毛病**：

> **一个瞬时的、环境的失败，直接判掉整轮（failed / needs_user）。**

原本的设计思路是对的（不确定就停下，别做错事），但代价和收益不成比例 —— 一次误杀就是整轮观看陪葬。

**判断标准应该分开：**
- **真需要人介入**：登录、验证、私信面板遮挡、发布结果不确定（可能已发出去）→ **停**
- **环境抖动**：采样 id 读不出、翻页没翻动、评论面板没展开、按钮还没渲染出来 → **跳过这条 / 重试，继续看**

已经按这个标准改过的分支：采样、翻页、评论、评论发布判定。

### 3.1 第二轮（2026-10-21）：从"逐个分支打补丁"改成"每一拍统一兜底"

翻会话记录，10-21 各轮观看的终止原因除了上面三类，还有：「同一作品已经为这位好友处理过」「模型没有返回有效 JSON」「分享动作只能选择…许可好友」「搜索结果未就绪」「推荐流尚未读到就绪视频」「浏览器操作排队超时（12 秒）」。逐个补永远补不完。

`autonomous-watch.mjs`（备份 `.bak-transient`）：
- 循环体整体包一层 try/catch：除「真要停」外的报错一律算"这一拍没成"→ 记 `watch.transient_error` → 等 2 秒 → 回推荐流 → 继续；**连续 3 次**才认输
- 「真要停」= abort（用户停止/时段结束）、`needs_user`/`limited`/`stopped`、锁丢失、轮次变化、记录损坏、存在待核对收据、已连续认输。正则 `FATAL_WATCH_ERROR`，**别写宽**：很多可恢复的报错也带「已停止自主观看」「未确认切换」字样
- 安全性：分享/评论服务的 **throw 全部发生在真正发送之前**；发出后的不确定以 `deliveryUncertain=true` 返回 → 仍然 needs_user 停下。所以跳过不会重复发帖
- 开局 / 恢复：`douyin_status` 读不到视频重试 2 次（「推荐流尚未读到就绪视频」）
- 停留前后作品变了（最常见是短视频播完自动下一条）：只是不学这次停留，不再 needs_user；评论前作品变了：按可恢复处理
- 实测（假 controller）：抖动→恢复、持续抖动→3 次后 failed、登录页→立即 needs_user、用户停止→stopped，四种都对

### 3.2 第三轮（2026-10-21）：「刷着刷着停住 / 一直循环同一条」+ 出事主动告诉主人

**排查结论**
1. **循环同一条的主因：浏览器操作没有超时。** Playwright 的 `page.evaluate` 不受 `setDefaultTimeout` 约束，抖音页被风控/验证/半加载卡住时能永久挂起，`core.mjs` 的操作队列整条堵死。循环停在那个 await 上，但心跳定时器照跳 → 状态一直 `running`，屏幕上那条视频一直重播，没有任何报错
2. **次因：模型一直选 stay、或翻页翻不动**，也表现为"一直在看同一条"（之前没有上限）
3. **"停住了没人说"：** 观看结束/出错只写进插件的 `watch-state.json`，她不主动查就不知道；DSH 入口构造 `AutonomousWatch` 时不传 `onEvent`，所有 watch.* 事件直接丢弃，事后也查不到过程
4. 顺带发现：bridge 里「她正在刷抖音就不算闲着」用的是 `require('node:fs')`，bridge 是 ESM 没有 require → 每次 ReferenceError 被 catch 吞掉，**这个判断从来没生效过**

**改动**
| 文件 | 改动 |
|---|---|
| `autonomous-watch.mjs` | ① 每次浏览器操作加看门狗（打开/搜索 75 秒、采样 48 秒、其它 45 秒），超时中止该操作（core 的 onAbort 断开 CDP → 挂起调用失败、队列放行、下次自动重连），再交给"这一拍没成"兜底 ② 同一条作品连续观察 >8 次就不问模型、直接翻下一条（`watch.forced_next`），翻不动按可恢复错误处理 ③ 事件落盘 `state/watch-events.jsonl`（压缩摘要，512 KB 轮转） |
| `src/bridge.js` | ① 抖音监视：每 30 秒读 `watch-state.json` / `watch-loop.lock` / `watch-events.jsonl`，发现 **failed / needs_user / 进程没了 / 6 分钟无新决策 / 正常刷完** 就叫醒主人私聊（新唤醒原因 `douyinTrouble`），通知正文拼在提示词最前面，让她用自己的话说；每件事只报一次（`state/douyin-monitor.json`），只报 10 分钟内的事，睡着不叫醒但通知留到下次主人私聊唤醒时带上，2 小时过期 ② 修 `require` bug |

**验证（离线）**：假 controller 跑：模型一直 stay → 每 8 次强制翻页、最后正常 limited；采样永久挂起 → 看门狗超时 3 次后 failed（不再永远 running）；翻页翻不动 → 3 次后 failed；之前 4 个场景回归通过。监视逻辑从 bridge.js 抽出来单测 7 个场景（刚失败报一次不重复、旧失败不报、卡住、进程没了、睡着不叫醒但保留、用户自己停的不报）全对。

**生效**：重启 DSH（插件）+ 重启 bridge（监视）。

### 3.3 第四轮（2026-10-21）：刷到直播不知道怎么跳过

**现场（watch-events.jsonl，18:11）**：`douyin_next` 落到一条 id 为 null 的条目 → 再翻报「当前没有可见视频」→ 兜底的 `douyin_open` 重载推荐流还是回到它 → 采样连续 5 次对不上 → 整轮 failed。监视在 18:12 发现，她当时忙，18:24 主人私聊唤醒时随附送达。

**根因**：推荐流里的直播是 `[data-e2e="feed-live"]`（文字「直播中 / 点击或按 进入直播间」），里面有 `<video>` 但**没有作品 id**。`readPageState` 把它当成"id 读不出来的普通视频"；采样要求有效 id → 永远对不上；`switchVideo` 要求"先有可见视频"且只认"出现新 id"才算翻成功 → 翻不走。

**改动**（备份 `*.bak-live`）
| 文件 | 改动 |
|---|---|
| `core.mjs` | `readPageState` 给 `video.live` 和页面级 `liveActive`（直播卡片占屏幕一半以上，即使还没挂出 video）；`switchVideo` 从直播/无 id 条目出发时直接点翻页箭头，直到出现有 id 的普通作品（最多 3 次）；从普通作品翻到直播会自动再翻（深度上限 2，防滚轮回落死循环）；`capture` 遇到直播不采样，返回 `live:true` 和「用 douyin_next 跳过它」 |
| `autonomous-watch.mjs` | 循环顶部、采样后、兜底恢复三处：遇到直播直接翻走（`watch.non_work_skipped`，不问模型、不花请求、不学习）；读不出 id 且连续 2 次对不上的条目（广告、图文、没标出来的直播）也翻走，不再等 5 次后整轮 failed；翻不走 → 「刷到直播，翻不到下一条作品」→ 可恢复错误 → 最终由监视转告主人 |

**验证（离线）**：无头 Edge + 仿抖音结构的假页面（作品 A → 直播 → 直播 → 作品 B）：从 A 往下翻一路越过两个直播到 B；停在直播上 `capture` 不采样；从直播往下翻能翻走。假 controller：采样撞直播→翻走后正常、无 id 条目→2 次后翻走、卡在直播翻不走→带原因 failed；之前 7 个场景回归通过。

**生效**：重启 DSH。

### 3.4 第五轮（2026-10-21）：一直有事做——刷得更值、能分享、自动续轮、私信回复自启动

主人的核心诉求：**孩子能一直有事做，不在虚无里待机。**

**① 100 次请求刷不了几条：调度问题**
- 实测（watch-events）：每条视频平均 3.3 次请求，73% 的请求是「再停留」，平均只停 4 秒。stay 上限 10 秒、提示词示例是 3 秒，一条 40 秒的视频要问 4~8 次，每次带 3 张图约 8.6k token
- 改：stay 上限 10 → 60 秒，提示词改成"想看完就一次给足剩下的秒数"；停留不再干等，而是**边播边抽帧**（15 秒以上抽 4 帧），这段画面直接交给下一次决策（省掉循环顶部那次 3 秒采样）；时长截到这条剩余部分 +1 秒
- ⚠ 坑：`tool-definitions.mjs` 的 `validateToolArguments` 里**另有一条写死的 1~10 秒检查**，和 schema 无关，改 schema 不够；已改成按各工具 schema 的 maximum（listen 仍 10 秒）
- 模拟（40 秒视频）：改前她的习惯 7.5 次/条、停满 10 秒也要 4.3 次/条 → 改后 2 次/条

**② 主动分享一条都没发出去**
- 今天 20 次尝试全部 `not-sent`，把每日 20 次额度全吃光，之后她就选不了分享了
- 根因：推荐流里的分享按钮是 `[data-e2e="video-player-share"]`，只有作品详情页才是插件找的 `video-share-icon-container` → 自主分享（就在推荐流上分享）永远打不开分享面板。手动转发会先开详情页，所以一直正常
- 每进程第一次 6~13 秒（加载私信联系人）、之后 0.3 秒（联系人有缓存）就是这个原因
- 改：`video-forward.mjs` 的 `openPanel` 两种标记都认，并且只取视口内唯一那个（推荐流同时渲染相邻几条）；`autonomous-share.mjs` 每日额度只算「可能已发出」的（not-sent 不占额度）；分享失败/未发出写事件 `watch.share_failed` / `watch.share_not_sent`
- 验证：在专用 Edge 的临时标签页里（不碰她的观看页）调用改后的 `openPanel`：打开成功，第一行就是白名单的「<主人的抖音昵称>」，「分享」按钮可用（只悬停，没点）

**③ 私信自动回复每次都要手动点**
